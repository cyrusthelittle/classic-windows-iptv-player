# Saved data, migration and rollback

Normal Windows installs store accounts, playlists, cache and update state in `%LOCALAPPDATA%\ClassicWindowsIptvPlayer`, separate from binaries. `AppDataPaths` pins this root for the process. Settings, protected account/channel/guide/recording-index data and feedback outbox use this root. Recordings and logs stay in `Recordings` and `logs` beside the executable. The updater stages under `AppDataPaths.Updates` and never replaces the profile root.

Use **Help → Open logs folder** to open the `logs` directory beside the program executable. Each launch creates a `session-*` folder containing `app.log` and any crash logs. This location applies with the normal profile and when a data-root override is set. The executable directory must be writable for logs to be saved.

Accounts and playlists remain in the Windows user data folder even when the executable is moved. `CYRUS_IPTV_DATA_ROOT` can override their data root with an absolute directory, without importing executable data; this is suitable for an explicitly chosen existing data root and isolated fixtures. Child processes inherit it. Relative overrides fail rather than resolving unpredictably. Do not change it during a running process.

On first launch, legacy account settings, cache and playlist files beside the executable are copied into a staging directory under the user data root. Recordings and logs remain in place beside the executable. Links are refused. Original account/playlist files are never changed; retained account/cache snapshots are protected for the same Windows user. Protected credentials cannot be moved to another Windows user or machine merely by copying files.

Settings, primary/backup caches, recording indexes and pending feedback decrypt/validate on staging copies before commit. Corrupt primaries may recover from validated backups there. Interrupted recordings are finalized on staged indexes. A complete stage is committed by a directory rename under a per-root cross-process lock. Failure retains the stage and source and aborts startup with recovery guidance; it never opens empty accounts instead. Retry creates a new stage from the unchanged source. Existing current-root settings always win over accounts bundled beside a later binary, even when current settings are corrupt. An established orphan root without settings/backup fails closed. A marked, unsaved first run can retry after login cancellation; the first settings save removes its pending marker.

Recordings use the `Recordings` folder beside the executable. Previously configured recording files and local playlists are copied into their current destinations when settings load; originals remain available for recovery. Recording-index paths and local playlist references are updated to the imported copies. Feedback destination bootstrap remains install-supplied and takes precedence over an older saved endpoint.

Before a future schema upgrade, retain a protected snapshot and check schema compatibility before writing. Current settings loaders reject newer schemas; migration also rejects newer recording-index schemas. Automatic rollback must use the matching pre-upgrade snapshot in a separate recovery root, not feed newer state into an old binary or overwrite newer user data. For manual rollback to an older executable, use the retained original install data from its retained app-folder copy, or restore a compatible snapshot into a separately chosen absolute override root. `pre-migration` preserves protected original bytes; invalid originals may remain invalid and need a known good backup. Keep later recordings in their existing absolute folders.

Tests must set an isolated absolute override before touching App, AppLogger or ConfigStore, or pass isolated executable/local-app-data arguments to `AppDataPaths.Initialize`. Existing WPF harnesses do this at Main entry. No tests should read normal user accounts or trigger real provider requests.

Historical user-data folders containing only `logs`, `startup-crash.log` and `runtime-crash.log` do not block migration of valid legacy accounts. Their diagnostics remain retained. A folder containing orphan caches or other saved files still fails closed when both account settings and their backup are absent. In that specific case the startup recovery dialog offers an explicit fresh start, with No selected by default. Choosing Yes creates protected default account settings atomically while retaining existing caches, logs and recordings in place. Reopen the app and enter account details again; this does not restore deleted credentials, favorites or preferences. The original installation's default recording destination remains selected. Corrupt settings, permission failures, competing instances and interrupted updates do not offer this reset.

Same-schema update installation and application-only rollback are implemented in [UPDATES.md](UPDATES.md). Runtime installations also use an installation lease so another data-root instance cannot race application replacement. An interrupted updater retains its durable blocking marker/job and application backup; recover those application files before normal startup. No saved-data snapshot is restored by this schema-compatible updater.
